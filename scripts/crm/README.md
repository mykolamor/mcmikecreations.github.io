# Hike CRM

A local web tool for editing the hikes of this site (sidecar JSON, post front matter, cover/GPX/GeoJSON files, generated data). It writes straight into the repo's `static/_projects/data-viz/hikes/` files, so review the result with `git status` / `git diff`.

## Start

```sh
pnpm crm
```

Serves on `http://127.0.0.1:8765` (loopback only, no login). The repo's `static/` folder is served read-only so cover previews work.

The server has no request timeout (Node's default cuts requests after 5 minutes), so a video upload of up to 2 GB can take as long as the link needs. Videos are streamed to a `.upload-*.part` file next to their target (gitignored) and renamed when complete; an aborted or refused upload leaves nothing behind.

### From a phone or another machine

Forward the port over SSH and open `http://localhost:8765` locally:

```sh
ssh -L 8765:localhost:8765 <host>
```

The layout switches to a bottom tab bar below 720 px width.

## Headless commands

```sh
pnpm crm help
pnpm crm <command> [args] [--dry-run]   # --dry-run: every command but check
```

`pnpm crm` with no command (or only flags, such as `--port 8766`) starts the UI as above; a first word that isn't a flag runs that command without the UI and exits. Commands load the same server code through Vite (with its own dependency cache, `node_modules/.vite-crm-cli`, so a UI running beside them is not disturbed).

Each command prints one line per changed file, `<path>: <what changed>`, then a summary line; warnings and errors go to stderr. `--dry-run` (every command but `check`, which writes nothing anyway) prints the same lines and writes nothing. A second run right after the first changes nothing. Exit code 0 on success (nothing to do included), 1 on a real failure (a post or GPX that can't be read; the other posts are still handled and the failing file is named), 2 for an unknown command or flag. Files are written atomically, and a write changes the doc version, so a UI open on the same post gets the conflict banner instead of saving over it.

| command   | does                                                                                              |
| --------- | ------------------------------------------------------------------------------------------------- |
| `metrics [posts…] [--missing-only]` | `distance`, `ascent`, `descent` (m) and `duration` (moving minutes) from each post's recorded GPX into its front matter (3D distance; climbs counted from 2 m; an interval is moving at 0.5 km/h or more over the minute around it, gaps over 10 min never). Posts are `<date>-<slug>` names or `.md` paths, default every dated post. Planned tracks (no `<time>`) and posts without a GPX are skipped. `--missing-only` writes only the fields a post doesn't have yet; without it, values that differ are overwritten. |
| `terrain [--no-nodes] [--no-photos]` | `demEle`, the height the 3D map draws the terrain at, from the DEM tiles: on every located `images` entry of the posts and place docs, every `osm.json` element (`tags.ele` is left alone) and every `{lat, lon}` place in a `*.hike.json`'s `facts` (a post's front-matter `facts` aren't touched) and in `facts-library.json`'s records. A value that differs is updated, so re-running after the DEM tiles change updates every one; points off the downloaded tiles are skipped. In the sidecars new keys go right after `lon` and only those bytes change; the library is written back in its own byte-stable layout. `--no-nodes` skips `osm.json`, the sidecars and the library, `--no-photos` the posts. |
| `photo-times [posts…]` | Checks each photo's front-matter `taken` and places photos without GPS on the recorded track (port of the former `backfill_time.py`). A `taken` is believable when its UTC offset is the one most of the post's photos have, its local date is a day the recording spans (a planned hike: the post date), and, for a photo with its own GPS, the track was within 250 m of it at that time (before or after the recording: its first or last point; inside a gap: the line between the gap's ends). One that isn't is reported on stderr (`<post>: <key>: taken … not believable (why); left as is`) and never removed. A photo without GPS and a believable `taken` within 15 min of the recording, not inside a gap where the track moved, gets the track position, its `demEle` and `located: track`; a `located: track` photo that can no longer be placed loses `lat`, `lon`, `demEle` and `located`. An existing track position on the track's path within the second of its `taken` is kept (the old Python placed at millisecond times). Photo GPS is never touched. |
| `video-meta [posts…] [--refresh]` | `videos.<id>` for each YouTube video the body embeds as an image, `![…](https://www.youtube.com/watch?v=…)`, wherever it stands (its own line, inside a paragraph, a list item or a quote; not in code), as the site renders them: a link, or a `youtu.be` image, is not an embed (port of the former `video_meta.py`): upload date, duration, en/de/uk title and description, size, and a self-hosted poster with AVIF tiers. Only entries that are incomplete or lack their poster are fetched; `--refresh` refetches all and overwrites hand edits. An entry with no embed in the body is removed (the key goes with the last one); a private video gets `{unavailable: true}`. YouTube unreachable only warns and exits 0, so an offline deploy still builds. `--dry-run` fetches nothing and reports what it would. `CRM_YOUTUBE_STUB=1` serves the fixtures. |
| `images` | AVIF tiers (640/1280/2560 by long edge, those that fit) and the `images` entry's `w`, `h` and `blur` for every local image a post or place doc shows (the former `oneoff/avif-backfill.ts`). Only what is missing is added: existing tiers are never re-encoded, existing fields keep their values. A new entry is keyed by the bare file name for an image in the doc's own folder, else by its full href; an existing entry under either key is the one filled in. An image without its original (the Photos tab keeps only tiers) is fine when nothing is missing; otherwise it is listed as a missing source on stderr and the run still exits 0. |
| `blog-images` | The same for blog posts (`static/_blog/*.md`, translations excluded): AVIF tiers and `w`, `h`, `blur` for every local raster image (JPEG, PNG, WebP under `/images/`) in `image`, `imageFull` and the body. SVG and GIF are left alone. A new entry is keyed by the full href. Tiers already on disk (a hike photo a post borrows) are reused, not re-encoded. Only front matter changes, so a post's `dateModified` stays put. The site shows an entry with tiers as an AVIF `<picture>`; the markdown alt text is the caption and the `<img>` gets `alt=""` unless the entry has its own `alt` (written by hand). The `imageFull` hero takes its alt from the `imageAlt` front-matter field, else `alt=""`. |
| `translate-blog <post> <lang>` | Drafts a blog post's translation, `static/_blog/<post>.<lang>.md`, with DeepL (key as for Fill: `deeplKey` in `scripts/crm/data/settings.json` or `DEEPL_API_KEY`; `CRM_DEEPL_STUB=1` fills `⟨de⟩ …` offline). `<post>` is the file stem (`2024-03-01-ecs`) or the slug without the date (`ecs`). Translates `title`, `description`, an explicit `section`, and each block of the body; fenced and indented code and link reference definitions are copied byte for byte and never sent. A block DeepL can't give back intact stays English, with a warning. Refuses to overwrite an existing translation. `--dry-run` sends nothing. Review the draft before committing. |
| `check [--strict]` | Prints every problem, one `<file>: <level>: <message>` line each (stderr): each post's (as the UI's problem list), each place doc that doesn't parse, the OSM store's (the former `check-nodes.js`): elements sharing a lat/lon, a name or a wikidata id (warnings, naming the hikes that use each), sidecar `nodes` ids missing from `osm.json` (errors); and the facts library's (`facts-library.json`): a record or id the build would reject is an error, a record no hike uses (`use` of no entry, or for a stop no `at` resolving to its ref) a warning, `facts-library.json: warning: transport "x" is used by no hike`; each translation file (`<source>.<lang>.md`) that doesn't parse (errors); and, per non-English language, one `src/lib/hikes/i18n/<lang>.json: warning: missing "<key>"` line for each string its table lacks. The summary follows every line, counting missing strings apart (`3 warnings (plus 12 missing strings)`), then one count per language. Missing strings are warnings only. Exit 0; with `--strict`, 1 when there is an error (a failed site build counts; missing strings never do). |
| `prebuild` | The deploy's data step. First it removes the temp files a crashed write left under `static/` (`<file>.<pid>.tmp` of a process no longer running, an `.upload-*.part` untouched for an hour), one line each (`--dry-run`: only lists them); then `metrics --missing-only`, `photo-times`, `terrain`, `video-meta`, `images`, `blog-images`, `check`, in that order and in one process, `--dry-run` passed on. Stops at the first step that exits non-zero and returns its code. |
| `help` | The command list. |

## Map tab

Leaflet view of the hike. Base layers (OSM, Tracestrack Topo, Mapy outdoor) are picked from the layer control, top right; overlays are the route GeoJSON, GPX, bailouts, checkpoints, other hikes' checkpoints, the tile area, hike nodes and photo locations. An elevation profile sits under the map. At 390 px the side panel becomes a sheet below the map and the controls are at least 44 px.

Tools (buttons top left, or keys; keys are only accelerators and are ignored while typing in a field):

| key   | tool                                                                              |
| ----- | --------------------------------------------------------------------------------- |
| `I`   | Inspect: tap the map to list nearby OSM objects, add one as a node or checkpoint  |
| `O`   | Set origin: tap to move the map centre                                            |
| `C`   | Add checkpoint: tap to add one, snapped within 30 m to another hike's checkpoint, else this hike's nodes, else an OSM store element                  |
| `Esc` | Leave the active tool                                                             |

Side panel: view (origin, size in px with the km it covers; or drag the green corner of the square), reorderable checkpoint and node lists, and the node editor.

- **This post only**: origin, size and checkpoints have a "This post only" switch. On, the value goes to the post's front matter and overrides the hike's; off, the override is removed and the sidecar value applies again. An empty checkpoint list cannot be an override, so removing the last checkpoint turns "This post only" off. Nodes are hike-wide only.
- **Node editor / local tags**: a selected node shows its OSM tags (owned by OSM) and its local tags (yours, stored under `local` in `osm.json`, for example `visited`). A local value of `null` hides that OSM tag on this site.
- **Refresh from OSM**: re-fetches one node's OSM tags and shows what was added, removed or changed. Only `tags` are replaced; `local` is kept.

`osm.json` writes carry a version; if the file changed on disk since it was loaded the write is refused with 409 and nothing is overwritten.

### Settings and caches

- `tracestrackKey` (see Settings) enables the Tracestrack layer; without it the layer is listed as disabled.
- Mapy tiles are fetched through the tool and cached in `scripts/crm/data/tile-cache` (gitignored), capped at 200 MB (oldest evicted first).

### Network etiquette

OSM is called only from this tool, never from the site build, and only on an explicit action. An Inspect tap sends what one "Query features" click on openstreetmap.org sends: its nearby and enclosing queries to `query.openstreetmap.org/query-features`, carrying the `_osm_totp_token` cookie the site's own pages set (fetched from `www.openstreetmap.org/query` as the sidebar frame, kept until a minute before it expires — about an hour — and fetched anew once if query-features answers 401 or 403) (geometry clipped to a small box around the tap; each object placed at its point nearest the tap, an enclosing area at the tap and listed after the nearby objects, areas wider than 20 km left out). When that endpoint (or the token page) fails or takes over 15 s, the same nearby lookup goes to the Overpass mirrors instead (no enclosing areas then). A search or a refresh is one Overpass request. Requests send the User-Agent `mykolamor.com hike CRM (scripts/crm)`, and the Query features ones also openstreetmap.org's `Origin` and `Referer`; Overpass and the OSM API are paced (OSM API at least 0.5 s apart, Overpass at least 1 s), and when an Overpass mirror is busy (429, 502, 503, 504) or silent for 20 s the next is tried: overpass-api.de, overpass.private.coffee, overpass.kumi.systems, maps.mail.ru. Each fallback and skipped mirror is printed in the terminal running `pnpm crm` (lines starting `[crm]`), as is every server-side failure: one line for one reported on purpose (status 500 or above, such as "OSM is busy"), the stack trace for an unexpected one.

## Photos tab

Picks the post's photos from Immich, uploads or reuses images, fixes their time, position and alt text, and places pins. It needs a dated visit (a post) or a place doc; a hike without one shows a hint. If Immich is unreachable or not configured, a banner says so and Upload, Library and pins still work.

- **Place docs**: the source bar has a search box instead of the album select: Immich smart search for its text (prefilled with the doc's title), optionally narrowed by the date range (clear both dates to search all dates). Photos go to `static/images/projects/data-viz/hikes/places/<slug>/` as `<date>-NN.jpg`, `<date>` being the photo's local `taken` date, else today. Their links are kept under `places/<slug>.md` in `immich-links.json`. Badges are only no time / no location, "From track" is not offered, and `updated:` is never stamped.

- **Source**: the bar picks the Immich album ("Guess from the name" matches the hike slug against album names, "None" searches all photos) and a date window (default: the post's date ±1 day). Photos are grouped into bursts: consecutive shots at most 30 s and 30 m apart (the distance only when both have GPS). The burst grid is on the left (above on phones), the viewer and the burst's filmstrip next to it.
- **Viewer keys and swipes**: `←`/`→` (swipe left/right) move within the burst, `↑`/`↓` (swipe up/down) between bursts, `Space` (or the Select button) adds or removes the photo. Keys are ignored while typing in a field.
- **Adding**: an Immich photo becomes `<YYYY-MM-DD>-<NN>.jpg` in `static/images/projects/data-viz/hikes/stories/<post name without date>/`, NN being the next number after the post's highest. Only AVIF tiers are stored (`<key stem>-640|1280|2560.avif`, those that fit, long edge, q50) plus a blur placeholder; no original. The entry gets `w`, `h`, `lat`, `lon`, `demEle`, `taken` (local time with offset) and `blur`. If the photo is added but its Immich link can't be saved, a notice says so; link it later with Find in Immich.
- **RAW/DNG originals are not supported**: sharp can't decode them, so adding or uploading one is refused (400). Add the JPEG or HEIC version instead.
- **Upload / Library**: Upload adds a file to the post's stories folder, the topo maps folder or another folder under `static/images` (shared images take an optional credit and source URL; the credit line and an image line are appended to the end of the text, to be moved into place in Write). Library reuses an image already under `static/images`.
- **In this post**: the post's photos with badges (no time, no location, off route: more than 300 m from the route, outside track: taken outside the recording). Per photo: Pins, Fix time (an exact time, or several photos shifted by N minutes), Fix location (tap the map, from the recorded GPX at the photo's time, or drop), Alt text, Find in Immich (for photos without a link; ranked candidates by image similarity, confirm one to link; an asset already linked to another photo of the post is refused) and Remove (deletes the entry, its link and, for a photo in the stories folders that no other post or place uses, its tiers; tiers of topos and other `static/images` files are never deleted; refused while the text shows the photo).
- **Pin editor**: tap the photo to add a pin and choose the OSM element in the picker (hike nodes and nearby places; an element not yet in `osm.json` is added to it), drag to move, long-press or × to remove. Keys: `[`/`]` previous/next photo, arrows nudge the selected pin (Shift: 5×), `Del` removes it, `Esc` cancels a new pin or closes; in the caption field with unsaved text, `Esc` only leaves the field (a second `Esc` closes). On phones the editor is full screen with the list, caption and mini map under the photo.
- **`updated`**: adding or removing a photo of a post that is committed stamps `updated:` with today's date, once per day; the notice offers Undo. Pins, captions, alt text and fixes never stamp it.

### Immich

Set `immichUrl` and `immichKey` (see Settings). Time and position fixes of a linked photo are written back to the Immich asset (`dateTimeOriginal` as local time with offset, `latitude`/`longitude`); dropping a position is not, because Immich can't clear one. A failed write-back is listed under "Immich was not updated" and never blocks the front-matter write. Immich calls time out after 15 s (original downloads after 120 s); once Immich is unreachable, the remaining photos of that fix are listed with the same message without further calls. Positions taken from the track are not written back.

- **Thumbnail cache**: `scripts/crm/data/immich-cache/` (gitignored), capped at 1 GB, least recently used first out. Originals are not cached.
- **Links file**: `scripts/crm/data/immich-links.json` (gitignored) maps `{ "<post file>": { "<image key>": "<asset id>" } }`. It is what marks a photo as linked (write-back, "in the post" in the viewer). An unreadable file is moved aside to `immich-links.json.corrupt-<time>` instead of being overwritten.

```sh
CRM_IMMICH_STUB=1 pnpm crm
```

Serves Immich from `scripts/crm/server/fixtures/immich-stub/` (album "Stub hike", `stub-asset-1` with GPS and `stub-asset-2` without, both on 2026-09-27) in memory; write-backs change only the in-memory stub. ## Place docs

A place doc is `static/_projects/data-viz/hikes/places/<slug>.md`: front matter `title` and `description` (both required), `tags` and `aliases`, then a markdown body the site shows under "Places on this route" of every post that lists it in `places:` (or whose hike does). On the Open screen, "+ New place doc" creates one (slug: lowercase letters and digits, single `-` or `_` between them); the list under it opens one. A place doc has the tabs Details (its front matter), Photos (see above), Write and Preview. Its photos live in `static/images/projects/data-viz/hikes/places/<slug>/`, and `updated:` is never stamped on it. A place doc and a hike may share a slug; they lock, version and keep photos separately.

## Write tab

The post's (or place doc's) text in a CodeMirror editor, exactly as it is on disk: lines soft-wrap only, nothing is reformatted, and a save replaces the bytes after the front matter's closing `---` with the editor's text, byte for byte. Typing saves by itself after a short pause (as the other fields do); a hike without a post has no text. When the file changed elsewhere while you had unsaved text (IDE, another tab), the conflict banner keeps your text: "Copy my text" puts it on the clipboard before you reload.

Toolbar (on a phone: Bold, Italic, Link and Photo, the rest under More) and keys; `Ctrl+/` (or Keys) lists them all. On a Mac, Cmd instead of Ctrl.

| key          | does                                                       |
| ------------ | ---------------------------------------------------------- |
| `Ctrl+B`     | Bold `**…**`                                               |
| `Ctrl+I`     | Italic `_…_`                                               |
| `Ctrl+Alt+2` | Heading `## `                                              |
| `Ctrl+K`     | Link `[…]()`                                               |
| `Ctrl+Alt+G` | German `<span lang="de">…</span>`                          |
| `Ctrl+Alt+M` | Missing: the link at the cursor, or the selection, becomes `[…](/404/)` |
| `[[`         | Link hike: search every post, Enter inserts `[Title](/hikes/<date>-<slug>/)` |
| `Ctrl+Z` / `Ctrl+Shift+Z` / `Ctrl+F` | Undo / redo / find and replace     |

Quote and List are toolbar buttons only.

- **Media**: Photo inserts one of the doc's photos the text doesn't show yet (also listed in the side panel, or drag one into the text); Video uploads an mp4 (up to 2 GB) into the doc's folder as the next `<date>-NN.mp4` and stamps `updated:` like a photo; YouTube writes the post's `videos.<id>` entry (titles and descriptions in en/de/uk, poster and its AVIF tiers in `static/images/projects/data-viz/hikes/videos/`) and inserts `![title](https://www.youtube.com/watch?v=<id>)`. Each goes on its own line, with a blank line around it, where the cursor was when you started; one upload or fetch at a time, and leaving the tab cancels an upload (nothing is left half-added): switching tabs asks "Cancel the video upload?" first, and leaving the page warns. A place doc has no YouTube.
- **Chips**: every media line starts with a chip: the photo's thumbnail (tap it for the pin editor), the video's file name, the YouTube poster, or "missing" for `/404/`. The line's own text stays editable.
- **Place mentions**: after 3 letters of a word, a list suggests the post's place docs and the OSM elements in `osm.json` (nearest the hike first); it never takes the focus, so typing goes on. `Alt+↓`/`Alt+↑` highlight an option (on a Mac also `Control+N`/`Control+P`; Firefox and Chrome elsewhere keep `Ctrl+N`/`Ctrl+P` for themselves), and only then do `Enter` or `Tab` insert it: `Name (ele m)` for an element with an elevation, else `Name`. Plain arrows close the list and move the cursor; `Esc` closes it. Tapping an option inserts it too. Mentions the site will link are underlined with dots.
- **Side panel** (on a phone a sheet above the tab bar, folded at first): a mini map on the photo or mention at the cursor, and the photos the text doesn't show yet.

## Preview tab

The post (or place doc) rendered by the site's own `parseMarkdown`, from the files as they are on disk now (typing still queued is saved first; Refresh renders again), followed by its place docs as the post page shows them. It runs in a sandboxed frame without scripts: no maps, gallery or pins. Links that leave the page open in a new tab; in-page links (place markers, place doc links) stay in the frame. Front matter that can't be read (CRLF fences, no closing `---`, or YAML that doesn't parse) is reported (422, "front matter not readable") instead of rendered; the Write tab still gets its place suggestions then, without place docs.

## Facts tab

The hike's `facts` (in the sidecar) and this visit's (in the post's front matter), field by field; `docs/hike-data-reference.md` describes every field.

**The form.** Each top-level key of the facts schema (`src/lib/hikes/facts-spec.ts`) is a folded section, in schema order; one with content starts open. The fields are drawn from the schema: groups as frames, lists with Add, Remove (asking first when the entry has content) and ↑/↓, a list of months as twelve toggles, enums and SAC grades as selects (a value the list lacks still shows), dates with a "Today" stamp. Places, spots and GPX paths have their own picker (below); the route list (`legs`) has its own table (below). The form shows the edits queued or still saving on top of the doc (`web/facts/facts-state.ts`), so nothing jumps back while a save is in flight.

- **Scope**: "Hike defaults" edits the sidecar's `facts`, where the visit-only keys (`conditions`, `deviations`) show "Only a visit can set this"; "This visit" edits the post's (below). A hike without a post has only its defaults.
- **Reload** (header, beside Save): reads everything from the files again, for an edit made outside the CRM. It saves what is queued first (the doc and its open translations); if something still can't be saved (a conflict, a failed save) or a running upload would be cancelled, it asks before going on. It reloads the whole page, since each tab reads its own data too, and reopens the tab it was on (`sessionStorage` `crm.reloadTab`).
- **Changes made outside the CRM** are found by themselves every 30 s and when the window gets the focus back (`checkFresh` in `web/doc-session.ts`). The doc's `version` (the sidecar and the post) changed: an idle view takes it ("Changed elsewhere — reloaded"), one with unsaved edits gets the conflict banner. `GET /api/doc` also gives `deps`, the version of the other files the views read (the route's GPX and GeoJSON, its bailout GPX files, `osm.json`, `facts-library.json`; `depsVersion` in `server/files.ts`), kept apart so a write to them (the CRM's own too) never makes a doc save a conflict. When only `deps` changed, the doc keeps my pending edits and takes the new `deps` and `files`; the Map tab, the Facts preview and shared records, and the generated metrics read again. It says "Route or shared files changed elsewhere — reloaded" unless this page sent a write since the last look (`ownWrites` in `web/api.ts`: any request but a GET), which was then likely its own. Photos and place docs aren't watched: use Reload.
- **Languages**: a text shows English beside the CRM's second language (stacked on a phone), picked in the app header (see Translations). A site with no language but English shows English alone, with no picker. Clearing the English while a translation is there is refused in the field ("English is required while there is a translation") and nothing is sent.
- **Adding** shows one new entry at a time; it is written with its first value, so an empty entry never lands in the file.
- **Conflict**: with facts edits unsaved, the conflict banner adds that list edits may land on other entries if the file changed (they address entries by index).

**This visit.** The post's facts over the hike's, as the merge lays them (`web/facts/inherit.ts`). A value the visit doesn't set shows the hike's, greyed, with "Override" (the visit's value starts equal to the hike's; for a text, its English) and "Remove for this visit" (`null`, shown struck through with "Undo"). An overridden value has "Reset to hike", which removes the post's key. A text's languages merge one by one: one the visit leaves out shows the hike's as a placeholder.

- **Lists paired by entry** (those with identity fields in the schema, such as `water` or `stops`) show the hike's entries, then the visit's own, paired as the merge pairs them: keys read the values as the site does before resolving places (trimmed, names normalised, `km 1` and `{km: 1}` alike, a spot's `{name}` as its name, a text as its English), and each post entry folds into the first row with its key, several shown merged with edits going to the first. Editing a field of a hike entry writes a post entry with that entry's identity fields (`at`, `name`, `use`…, the fields its merge key is built from) and its required fields (which the site checks on a post's entry too; not for an entry using a shared record) plus the field, so the merge pairs it with the hike's entry instead of adding a second one; the identity fields can't be changed there, the required ones can. "Hide for this visit" writes the identity fields with `remove: true`; "Undo" and "Reset to hike" remove the post entry. A `remove` that matches no hike entry shows the site's warning.
- **Known gap:** a place named in one file and given by ref (or lat/lon) in the other pairs on the site only once resolved against OSM; the tab shows two rows.
- **Known gap:** renaming a spot written as a plain string with "Just a name" replaces the string. If that string was the name of an OSM element (so the site placed the spot there), the spot loses its position; use Search to keep a place and give it its own name.
- **Other lists** are replaced whole by the post's: "Own list for this visit" copies the hike's list into the post, "Use the hike's list" removes it again.

**Posts** (`web/facts/PostField.svelte`): a field naming a post (`plan.alternatives.easier`/`harder`/`similar` entries and a variant's `link`, marked `ref: 'post'` in the spec) shows the post's title with its name, or "(no such post)"; Pick or Change opens the Write tab's post search (title, date or slug, newest first; arrows and Enter pick) and writes `<date>-<slug>`; ✕ clears it.

**Places** (`web/facts/PlaceField.svelte`, values in `web/facts/place-value.ts`). A place shows its value in words (every written form: a node name, `km 7.5`, `{ref}` named from the store, a point, a spot's `{name, at}`) with Pick or Change and ✕; Change opens three ways to give it:

- **Search**: by name, or a pasted id or link, with two buttons. Typing (or Enter, or **Search store**) searches only the store, matching any part of any `name*` tag, with no network call (`source=store`); **Search OpenStreetMap** queries Overpass, or the OSM API for a pasted id (`source=osm`). With the doc's route, both lists are sorted by distance from the route (the shortest distance to any of its segments) and OSM is searched around the route's midpoint (`GET /api/osm/search?q&source&slug[&date]`, `source` being `store`, `osm` or `all`, the default; a post's `filePath` is respected). An element not in the store yet is added to it first (`POST /api/osm/add`, with its name, coordinates, height and `demEle`, retried once on a stale store version; not to the hike's `nodes`), then written as `{ref}`.
- **On the map**: a small map of the route on the Map tab's base layer; tap the place and name it. It is written as `{lat, lon, name, demEle}` (7 decimals; `demEle` from `GET /api/terrain/height`, left out off the tiles).
- **At km**: a distance along the route, written as `{km}`.

A point that is the value shows its name as a text under the value, English beside the session language; clearing it leaves the point unnamed (a named spot's `at` has no such field: the site shows the spot's name). A spot also has **Just a name** (a text): a plain string spot that isn't a km is its name, shown there and replaced by `{name}` when typed; typed on a placed spot (a km string or an object place) it writes `{name, at}` with the place kept; a named spot keeps its name when a place is picked, and clearing the name keeps the place. A ref is named from the store wherever it shows, the hike's greyed values included. A bailout's `route` (a GPX) is a select of the doc's bailout files (the served path); **Upload new GPX** beside it writes a new file to `gpx/bailouts/` (`PUT /api/files/bailout/new?slug`, named after the uploaded file: lower case, umlauts as `ae`/`oe`/`ue`, anything else `_`; an existing name gets `-2`, `-3`, nothing is overwritten) and picks it. The doc is written only when the form saves the bailout; a file uploaded but never used stays in the folder. OSM is called only by a search, never when the tab or a picker opens; for an offline try, start with `CRM_OSM_STUB=1` and search for "stub".

**The route list** (`web/facts/RouteList.svelte`, logic in `web/facts/route-list.ts`). A table of `legs`, one row per entry: from → to, SAC, via ferrata, climbing, terrain, marking, optional, note, and the toggles "In table" and "On profile"; on a phone each row is a card. A table entry's from is where the previous table entry ends ("Start" for the first), shown and not editable; an entry off the table shows its own ends, an absent one as "Start" or "End". Tapping a row selects it (the tab keeps the selection, as its index in the scope's merged list) and opens its other fields in the form below the table. ↑/↓, + (add after) and ✕ edit the order; a new entry is inserted with its first value.

- **Toggles** write what the site needs: off the table writes `inTable: false`, `onProfile: true` and the entry's effective `from`; back into the table removes `inTable` and `from` (it needs a `to`). A default (`inTable: true`, `onProfile: false`) is written by removing the key. "On profile" can't be turned off on an entry off the table, which would show nowhere.
- **This visit**: the rows are paired as in other lists (the hike's entries, then the visit's own). A hike entry's toggles are its identity there and read-only, with "Hide for this visit" and "Reset to hike" in place of ↑/↓ and ✕; the visit's own entries move among themselves. `legs: null` shows the hike's list struck through with "Undo". A row's note merges with the hike's per language, as on the site.
- **The selection** follows its entry: through ↑/↓ (the entries it passes shift too), ✕ and "Hide for this visit" (the selected one removed clears it), and "Undo" of a hidden entry. A doc the tab didn't save (a "Changed elsewhere — reloaded", or "Reload (discard my unsaved)") clears it.
- **Folding**: in "This visit", turning a visit's own entry off the table can fold it into a hike row off the table with the same from and to (the merge pairs entries off the table by their span); the site does the same.

**The preview** (`web/facts/FactsPreview.svelte`, logic in `web/facts/preview.ts`). Beside the form from 720 px; on a phone a sheet above the tab bar that folds away (folded at first), like the Write tab's side panel. It draws the facts as the post page does: the elevation profile with the site's `initElevationChart` (the bands and pins of `buildFactsOverlay`, in English), and a small map on the Map tab's base layer with the route and the facts' marks (`web/facts/facts-layer.ts`: the site's pin icons and popups, hazard stretches, dashed bailout routes).

- **Draft**: after an edit (debounced 300 ms) it posts `POST /api/facts/preview` with the local facts of each scope that has edits queued or saving (`null` when the edits left a scope none); the server reads the files for the rest. A hike without a post previews the sidecar alone. A visit's removals ("Remove for this visit", a `null`) show as they are queued, texts too. An answer to an older request arriving after a newer one's is dropped.
- **Errors**: the site's `FactsError` (a half-typed time, an unknown value) shows above the preview, and the last good drawing stays.
- **Highlight**: the route list's selected entry is an orange band on the profile's hazard row ("Selected") and an orange line under the route on the map, which fits to it. Its stretch is the km of the entry's resolved ends (an absent end is the route's start or end; an end not on the route, no highlight), the same as its profile band. In "Hike defaults" on a post, the entry is found in the merged list the preview draws (none when the visit hides it).

**Shared records** (`web/facts/SharedRecord.svelte`, logic in `web/facts/shared.ts`). Each entry of `stops`, `access.transport`, `access.lifts`, `access.parking` and `access.tickets` shows the record of `facts-library.json` it starts from (its `use`; a stop, the record of the OSM element its `at` names: a `{ref}`, or a name the preview resolved to one) and "used by N hikes" (N counts hikes; a hike's posts count once).

- **The record's values** show under the entry as inherited (greyed, with "Override"); the entry's own values override them, and "Reset to record" removes the entry's own. The entry's `use` is read-only while it finds its record (the line above names it); a `use` naming no record stays editable, to fix or clear. An edit writes only that value into the entry, never the record's others, so the entry keeps following the record. In "This visit", a hike entry shows the record with the hike's entry over it, and entries pair through their records as on the site (a `{use}` entry with a visit's entry that spells the record's identity out).
- **Use a shared record** (on the scope's own entries, a new one too): that kind's records, filtered by text, each with "used by N hikes". Picking one writes `use`; for a stop, which attaches by place, it writes `at: {ref}`.
- **New shared record** (an entry with content and no record): asks for an id, prefilled by the rule the library's first records got (`shared/library-id.ts`: transport `<mode>-<line or from>-<to>`, the others their English `name`, else `at`, slugified; `-2`, `-3` on a clash with a record some doc uses: one no doc uses, such as one left by an earlier try whose entry wasn't saved, is replaced, and the panel says so); a stop's id is its OSM ref, so it needs a place from the store. The entry's fields move into the record (written first), and the entry becomes `{use}` (a stop keeps only its `at`).
- **Edit shared record** opens the record in the same form, kept locally until "Save shared record" writes it whole (texts by the same English-plus-one rule). A record more than one hike uses asks first: "This changes N hikes: …", naming the docs. The save is made on the library version the draft was copied from (the record as Edit's own read found it), so a change to the library made elsewhere since is refused (409) and the draft stays open; the read for the question never becomes the save's version. A read that started before a write's answer is dropped when it answers later.
- **Usage** is loaded with the tab and read again when Edit or New opens, before Save asks (so a record this doc just took counts), and once the edits that may change which record an entry takes (its `use`, a stop's `at`, a whole entry or list) are saved; other saves don't read it again.
- **`GET /api/facts/library`** answers `{ version, library, usage }`: the version is the sha1 of the file's bytes; `usage` lists, per `"<kind>/<id>"`, the docs (`<date>-<slug>`, or `<slug>` for a hike with no post) whose reading takes the record, read as the build reads them (`libraryUsage` in `server/facts-read.ts`; kept while the hike files, the route GeoJSON and bailout GPX files, the store, hikes.json and the record ids stay the same, since reading every doc takes seconds).
- **`PUT /api/facts/library/record`** (body `{ kind, id, record | null, base }`) checks the record as the build does (400 with the site's message), and writes the file byte-stably. A stale `base` (another tab or the CLI wrote first) answers 409 and nothing is written; the tab reads the library again and says so. `null` deletes a record, refused (400, naming them) while a doc takes it.

**Near-duplicates** (`web/facts/NearDuplicates.svelte`; grouping and merge in `lib/facts-near-duplicates.ts`, which the extraction one-off imports too). At the bottom of the tab: the entries of the library kinds that this hike (its sidecar or a post) shares by key with another place but not by content (stops by OSM ref, transport by mode/from/to/line, lifts and tickets by name, parking by name and at), each entry with its file, path and its values of the fields the group disagrees on. A group whose entries all take one record already differs on purpose and isn't listed. A group is known by its `id`, the exact key (`<kind>|<the key fields as JSON>`), so two whose labels match (a translation apart) stay two.

- **Merge into a shared record**: pick the entry to keep and an id (prefilled by the rule above; a stop's is its OSM ref; a group some of whose entries take a record already, from a merge that stopped part way, proposes that record's id). The chosen entry becomes the record (minus `use`, a stop minus `at`), and every entry of the group becomes `{use}` (a stop keeps its `at`) plus the fields where it differs from the record, texts compared as written, so no page changes. An entry that lacks a value the record has can't say "none" over it in a sidecar, so it stays as it is ("kept: has no note"), and the others are merged. Before anything is written, every page that reads a touched file (for a stop record, every page) is read as the build reads it with the new record and must read the same, else 400 and nothing is written. Then the library is written (on the version read when the merge began: 409 if it changed), then each file, loaded fresh and saved through `saveOps` on its current version after checking its entry is still the one grouped. A failure names its file; the files before it stay written, and the group stays listed: merging it again with the same id finishes it (an entry converted already writes nothing). An id is taken when a hike outside the group takes its record, or when hikes take it and the record would change; a record no hike takes is replaced. Merge waits while edits are unsaved, and until the shared records are loaded (the id comes from them); afterwards the doc (quietly: the change is the tab's own), the shared records and the groups are read again.
- **Keep apart** adds the group (`{kind, key, group}`, `group` its id) to `scripts/crm/data/near-duplicates-kept.json` (gitignored), and it is no longer listed.
- **`GET /api/facts/near-duplicates`** answers the groups (`{ id, kind, key, record?, entries }`), read fresh from the files (under a second); **`POST /api/facts/near-duplicates/keep`** takes `{ kind, key, group }`; **`POST /api/facts/near-duplicates/merge`** takes `{ group, chosen: { file, path }, id }` and answers `{ ok, library, files: [{ file, status, error? }], kept: [{ file, path, reason }] }` (500 with the same body and `error` when a file failed after the library was written).

**Offline check.** `CRM_OSM_STUB=1 pnpm crm` serves OSM searches and adds from the stub fixtures (search for "stub"); nothing in the tab calls OSM on load. Edits, records and merges still write the real files, so `git checkout` the sidecar, post, `osm.json` and `facts-library.json` afterwards.

**Writing.** Each edit is one value under `facts`, saved like any other field (the save queue, 409 when the doc changed on disk) and minimal-byte: only the bytes of the value set or removed change. In the sidecar, untouched members keep their text (number spellings like `1577.0`, one-line arrays), a new key is spliced in after the last one, and a removed list item leaves a one-line list on one line. In the post, nodes that stay equal keep their bytes and comments; a map is edited per key, a list keeps the node of every item equal to an old one (so a reorder only moves entries), new maps are block style and new lists of scalars flow style (`[a, b]`), and a new `facts` key goes before `images:`.

- **Texts**: always written as a `{en, de…}` map, English alone included (`{"en": "…"}`), keeping every language already there; a plain string written by hand is still read, and the first edit turns it into `{en}`. Clearing a translation removes its key; clearing the English while a translation exists is refused (400, "the English text is required while the field has a translation (de)").
- **Removing** an entry or a key also removes a list, a map or `facts` that it leaves empty: never a `[]`, `{}` or empty `facts:` behind.

**Reading.** `server/facts-read.ts` reads a doc's facts as the post page does (the same `readHikeFacts`, with the page's nodes, origin, height, route coordinates, distance factor, bailout GPX and the library file), from the files as they are now; the CRM never validates facts itself.

- **Problems** lists the site's `FactsError` of the hike or post as an error, and each facts warning as a warning.
- **`POST /api/facts/preview`** (`?slug[&date]`, body `{ draft: { hike?, post? } }`) reads the facts with the draft in place of that file's `facts`. A half-typed value answers 200 with the site's message in `error` (and `facts: null`), so the preview keeps its last good drawing.
- **`GET /api/terrain/height?lat&lon`** answers `{ demEle }`, the height `crm terrain` would write (`null` off the downloaded tiles).
- **`null`** is written only in the post (the merge's "remove the hike's value for this visit"); in the sidecar it is refused (400).

## Claude tab

A terminal running Claude Code in the repo root, on this machine (not a cloud session), with your usual login, settings, skills and memory. There is one session for the whole CRM: it belongs to the server, so leaving the tab, opening another hike or place doc, or reloading the page reattaches to the same session with its screen and scrollback (switch sessions inside it, `/resume`). The first visit after the server starts launches it; after Claude exits (`/exit`) the tab offers "Start again" and nothing restarts on its own. Stopping the CRM server ends the session.

The command is `claudeCommand` in settings.json or `CRM_CLAUDE_COMMAND` (default `claude`), for example `"claudeCommand": "claude-tum"`. It runs through an interactive `$SHELL -ic`, so shell aliases and functions work as in your terminal; it is read at each start, so a change applies on "Start again". Variables marking an enclosing Claude Code session (`CLAUDECODE`, `CLAUDE_CODE_*`) are dropped, in case the CRM was started from one.

The terminal is a WebSocket at `/crm-claude/socket` (`vite.config.ts`, `server/claude-terminal.ts`). Since it can run anything, only the CRM's own page gets in: a loopback `Host` (no DNS rebinding), an `Origin` on that same host (no other website), and a token from `/crm-claude/token`, made at each server start. Forwarding the port over SSH works as for the rest of the CRM.

## Translations

A translation is `<source>.<lang>.md` beside the post or place doc it translates (`2026-07-19-x.de.md`, `places/knorrhuette.de.md`): front matter `title`, `description` (and `aliases` for a place doc), each optional, then the translated body. The English file is never written by translating.

**Blog posts** (not in the CRM; write by hand or draft with `pnpm crm translate-blog`). A translation is `static/_blog/<date>-<slug>.<lang>.md` beside the English post, in a language of `src/lib/i18n/translation-name.js` (`de`, `uk`). Its front matter may hold only `title`, `description` and `section` (`article:section` in that language), each optional; anything else (`date`, `tags`, `author`, `image`, `imageFull`, `imageAlt`, `images`, `draft`, `updated`) is the English post's, and setting it fails the build. The body is the whole post translated, code left as it is; every local image or clip it shows must exist (`static/` or its AVIF tiers), image captions may be translated and `alt` comes from the English post's `images:` entry. A translation isn't listed, in a feed or the search index, and has no page yet (the `/de/blog/` routes come with the hike German pages). Editing it never changes the English post's `dateModified`.

- **One second language.** The CRM shows English beside one other language, the same everywhere: the select in the app header (shown when the site has a language besides English), remembered in `localStorage` (`crm.lang`). The first read takes the Facts tab's former `crm.factsLang`, else the first non-English language; the old key is left as it is.
- **A doc of its own.** `GET`/`PATCH /api/doc` take a translation as its source's params plus `lang=` (`?slug&date&lang=de`, `?place&lang=de`; a language the site doesn't translate into, or a hike without a post, is a 400). It is versioned and saved like any doc (409 on a stale base) and shares its source's lock and media folder. A translation not made yet reads as `exists: false`, empty. Its fields are `tr.title`, `tr.description` and, for a place doc, `tr.aliases`; clearing one (empty or blank) removes its key. A save the site wouldn't read is refused with the site's message (400).
- **Creating** (`POST /api/translation/create`, same params) writes an empty front matter, `---\n---\n`, never empty keys. It is refused when the source is missing (400) or the translation exists (409). A save is refused (400) too once the source is gone.
- **Writing one** (Write tab). Above the toolbar of a post or place doc, three buttons, "English | DE | Side by side" (DE being the second language): the first two switch the editor between the English text and its translation; the translation's session opens the first time you switch to it. Without a file, the view offers "Translate into German", which creates it (as above). With one, its Title, Description (and Aliases for a place doc) sit above an editor of its body, each saved like any field (blank removes the key). The editor works as for English: the keys, the German span, Link hike, the chips (the source's own folder) and place mentions; Photo, Video and YouTube aren't offered, since media are added in English first (copy their lines), and a photo chip doesn't open the pin editor. The translation's save state and conflicts share the header's status and the conflict banner, prefixed "DE:"; Save and leaving the page cover both files. Switching waits while an upload or fetch runs.
- **Side by side** (Write tab, the third button; without a file it offers "Translate into …" as above). One row per block of the body (blocks are separated by blank lines), English on the left and the translation on the right; on a phone each row's English sits above its translation. Media blocks (lines that are all `![…](…)`) pair by their set of hrefs and headings by their order among the headings; the text blocks between two such pairs pair by order, and the extras get an empty partner: "Add translation here" (type to add a block after the translation's block above) or "English has nothing here". The rows follow the English order; a block only the translation has sits where it is there. Each side is a textarea that saves its own file through its own session, as the editor does (the whole body, debounced). An edit is applied to the current body by the block's own text: where it was, else where that text alone makes up a block once; otherwise nothing is written and that file's conflict banner opens, so a change made elsewhere (the IDE, another tab, an upload's credit) is never overwritten at a stale offset. A block's trailing line breaks are dropped, and clearing it (or leaving only blanks) removes it and one blank line. The rows stay as they are while a textarea has the focus, a freshness reload included (the next keystroke finds its block again, or conflicts), and are paired again once the focus has left them; "Reload (discard my unsaved)" shows the doc's text again at once. Overwrite drops the edit being typed too (the conflict was that its block couldn't be found): the rows are paired again from the doc, and the next keystroke starts over from its row instead of raising the conflict again. While a side's file is in conflict its textareas are read-only, so nothing is typed that Overwrite or Reload would then replace. Editing an English block that has a partner shows "German may need the same change" on the partner, in memory only, until that block is edited or the view reloads. Media show as chips (the source's own folder); the English side also shows their captions, read-only, and the translation's side is a textarea too, to translate the captions (keep each `](…)` as it is: the line keeps its photo only so) (`web/write/pairs.ts`, `web/write/SideBySide.svelte`).
- **In the Write tab**, while the translation (or side by side) is shown, its problems are listed under it, checked again after each save. A failed first load of the translation offers Retry (a failed create doesn't: "Translate into …" stays).
- **Problems** (`GET /api/problems` with `lang=`) lists what `crm check` reports for the file, one error at a time in its order: a key or text the site refuses, else the site's error when its source is gone, else the first missing photo or clip. A file with CRLF front matter (the site reads it; the CRM can't edit it, 422) is a warning. A translation whose source was renamed or deleted has no doc to open it from, so it can only be seen in `pnpm crm check` (rename or delete it with its source).
- **Route words** (Details tab). Under Name and Description a second input, "Name (DE)", edits the second language's text of the sidecar. It is a field op with `lang` (a language the site translates into, on a translated field; 400 otherwise): that language's key is set inside the `name`/`description` map, a plain string becoming `{en, de}`; clearing it removes the key, and a map left with English only stays `{en}` (the Facts tab's Text rule). Without `lang` an op edits the English as before (refused while a translation exists if it would clear it). `GET /api/doc` gives `texts` (every language of each translated field; `fields` stays the English) and a save answers with it. Typing in one language never replaces a pending edit of another (they queue apart).
- **The translation's texts on Details** (a post's or place doc's Details tab). Under Title, Description (and a place doc's Aliases) a read-only row shows the translation's text in the second language, with "Edit in Write", which opens the Write tab on the translation's view. They are the translation file's, not the sidecar's, so they are edited there only. Details opens the translation's session as Write does (one load, the same session). A translation not made yet shows one line under Title instead, "No German translation yet. Translate in Write".
- **Label tables** (Open screen, "Label tables · DE"; `?strings=<lang>`). The site's labels and tag texts (`src/lib/hikes/i18n/<lang>.json`) as English | DE rows by dotted key (`facts.labels.summary`), the keys the table lacks first (the site shows those in English), with a filter. "Missing only" (on when the table lacks keys; "Show all" turns it off) shows just the keys it lacked when it was read, so a row being filled stays. A paragraph list edits as one text, paragraphs apart by a blank line. A row whose `{placeholders}` differ from the English warns. Typing saves the key after a pause; a blank text removes it (and a group left empty). `GET /api/strings?lang=` gives `{ version, en, own }`; `PATCH /api/strings` `{ lang, base, set: { key: value | null } }` changes only those keys' bytes, in the file's own layout (tab indent; a list kept on one line or one paragraph per line, a new one laid out as English lays it out). A new key goes after the nearest key before it in English order that the file has, else at the end of its group, its missing groups created. A string the site wouldn't parse is refused (400, naming the key), a stale base answers 409 ("Changed on disk — Reload"), a table broken by hand (JSON that doesn't parse) answers 422 with the parser's message, and English is never written (`server/strings-file.ts`, `web/strings/rows.ts`).
- **DeepL** (`server/deepl.ts`). `POST /api/deepl/translate` `{ lang, texts: [{ id, text, kind }] }` translates English texts into `lang` and answers `{ texts: [{ id, text }], refused: [{ id, reason }] }`; `GET /api/deepl/status` answers `{ configured, targets }` (the languages DeepL has a code for: `de` → `DE`, `uk` → `UK`, `cs` → `CS`). The key is `deeplKey` in settings.json or `DEEPL_API_KEY` (see Settings); a key ending in `:fx` goes to `api-free.deepl.com`, any other to `api.deepl.com`. Without one the route answers 503 `{ error: 'no-key', message }` and sends nothing, and the rest of the CRM works as before. Texts go 50 to a request, in order, with `tag_handling: 'xml'`. What must come back exactly is sent as `<x id="N"/>` and put back after (`&`, `<`, `>` escaped around them): for `markdown`, the markup and target of photo and video lines (YouTube too: the `![` and the `](…)`, the caption between them is translated, a credit link or mention in it kept), link targets (the `(…)`; the link text is translated), bare URLs, place mentions `Name (1234 m)` (less a leading English word such as "After"), inline code, HTML tags, `{name}` placeholders and the markers at line starts (`#`, `>`, `-`, `*`, `1.`); for `plain`, URLs and `{name}`; for `table`, `{name}`, whole `{x, select|plural, …}` forms, link targets and bare URLs. DeepL's numeric character references (`&#39;`, `&#x27;`) are decoded. An answer that loses, repeats or changes a placeholder, moves a line-start marker off the start of its line ("DeepL moved a list or heading marker"), turns a photo or video line into something else or changes its target ("DeepL broke a photo or video line"), or changes the number of lines, is left out and listed in `refused`, never returned. A text with nothing but protected parts isn't sent and comes back as it is. A quota error (HTTP 456), a rate limit (429), any other HTTP error or a network failure answers 502 `{ error: 'quota' | 'rate' | 'http' | 'network', message }`; no message holds the key. For an offline try, start with `CRM_DEEPL_STUB=1`: no key is needed, and each text comes back as `⟨de⟩ <text>` (after a heading's or list's marker, or a photo line's `![`).
- **What is still missing** (`server/translation-gaps.ts`, `GET /api/translation-gaps`). The Open screen shows one badge per language with something missing, naming the parts (`DE: Facts, Text`): on a hike its sidecar's, on a post or place doc its own. Inside a doc, a dot on the tab for the header's language: Facts, Write (a missing file or block, or a caption still English) and Details (title, description, the hike's name and description). A shared record the facts take counts, unless the entry states that text itself. A mirror source's title is a platform's name, which neither counts nor gets filled. Missing means what Fill would fill (it asks Fill's gather functions), so a translation gone stale after an English edit, or a stop written by name, isn't noticed.
- **Fill empty from English** (`web/fill/`). A button on each translation surface: the Write tab's translation (alone or side by side), the Facts tab (the scope shown), a shared record's edit form, the label tables and the route words (Details). Pressed, it gathers the English texts whose translation is empty, sends them to DeepL in one request (the server sends them on 50 at a time), and fills each answer in only if its target is still empty when the answer arrives: a text typed meanwhile is kept, and the answer for it is skipped. Nothing is ever overwritten.
  - **Write tab:** the translation's Title and Description when blank, and each English block without a partner, put after the translation's block above its row (as side by side pairs them); for a translation whose body is empty, every English block goes in, so it reads complete. Photo and video lines get their captions translated (the line's target stays the source's). A photo or video block the translation has exactly as the English has it (copied, caption still English) is filled in place with its caption translated; one whose caption was changed by hand, or that has no caption, is left alone. The body is saved as if typed (in the editor, one undoable change). Aliases aren't filled.
  - **Facts tab:** each text of the scope's own facts with English and no second language, as a text edit at its path; link texts (a link written as a bare URL has none), a point's name and a spot's name, each as the whole link, place or spot, as their own fields write them. **Shared record:** the same in the record's draft, which is saved with "Save shared record" as usual.
  - **Label tables:** the missing keys, typed in and saved after the pause as usual. **Route words:** the sidecar's Name and Description in the second language, as their `lang` field ops.
  - Each filled text is a **DeepL draft**: dashed and labelled "DeepL draft" (in the Write editor, a small label at the start of the block) until it is edited or the page reloads (one style, `web/fill/drafts.css`). Nothing marks it in the files.
  - The button is hidden for a language DeepL has no code for, and disabled without a key (it says how to add one). While working it shows the number of texts and is disabled. An error (no key, quota, rate limit, HTTP, network) is shown, and nothing is filled; so is a conflict raised while DeepL was answering ("resolve the conflict, then fill again"). DeepL's line breaks around a placeholder are undone first (`relayout` in `server/deepl.ts`): each photo line or marker opens its line again and a paragraph keeps its number of lines, re-wrapped; breaks that mean something (a hard break, an indent, a table, a fence) are never rebuilt. A text whose answer still can't be used is kept empty and listed with the reason under the button, remembered in `localStorage` per doc, language and button until "Dismiss" or the next fill there.
  - **Offline check:** `CRM_DEEPL_STUB=1 pnpm crm`, open a post, switch to its translation and press the button: each empty text fills as `⟨de⟩ …` without a key or a request to DeepL. (It writes the translation file like any edit: try it on a post whose translation you can throw away.)
- **Known gaps.**
  - Side by side: a Fill landing while an empty "Add translation here" cell has the focus can put the block typed there next to the filled one (both stay; delete one).
- **Adding a third language** (today the site has English and German):
  - add it to `LANGS` (`src/lib/i18n/translation-name.js`), its table `src/lib/hikes/i18n/<lang>.json` and its import line in `strings.ts`;
  - the conflict banner shows only the selected language's translation session, so a conflict in another language's open session goes unseen: give each session a banner of its own (or close a translation's session when the language is switched);
  - the label tables take their language from `?strings=<lang>` (the Open screen links one per language), and opening one picks that language in the header; the header's select moves the page to the picked language's table;
  - DeepL fills only a language with a target code in `scripts/crm/shared/deepl-langs.ts` (`de`, `uk`, `cs` now); without one the Fill button is hidden.

## Tests

```sh
pnpm test
```

Runs every `*.test.ts` under `src/lib` and `scripts/crm` (via `scripts/crm/run-tests.sh`).

```sh
pnpm check:crm
```

Type-checks the tool (`scripts/crm/tsconfig.json`: its `.ts` and `.svelte` files, with Node and Vite client types); it should report 0 errors. The root `pnpm check` doesn't cover `scripts/crm`. Type shims for untyped packages live in `scripts/crm/types/`.

## Data and fixtures

Everything under `scripts/crm/data/` is gitignored: `settings.json`, and `data/fixtures/` (for example `sample.heic`, used by the HEIC cover test; re-download it with `node_modules/.bin/jiti scripts/crm/fetch-fixtures.ts`, which needs the Immich settings). Tests that need the fixture skip or fail without it.
