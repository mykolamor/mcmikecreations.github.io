# Mit ECS das Rad neu erfinden

Kürzlich habe ich [einen Artikel von Kasey Speakman](https://dev.to/kspeakman/entity-component-system-an-old-new-thing-3224) über das Entity-Component-System (ECS) gelesen.
Darin wurden die Gemeinsamkeiten und Unterschiede zwischen der ECS-Architektur und der strukturierten Programmierung ausführlich behandelt. Es gab weitere [tolle Artikel](https://www.simplilearn.com/entity-component-system-introductory-guide-article) zu diesem
Thema, in denen grundlegende Ansätze zur Verwendung von ECS beschrieben und verschiedene Anwendungsfälle aufgezeigt wurden.

Da ich am Lehrstuhl für Data Science und Engineering an der TUM arbeite, betrachte ich
Systeme ohnehin eher aus einer datenorientierten Perspektive. Deshalb wollte ich einen kurzen
Beitrag über die Nutzung von ECS aus meiner Sicht verfassen und ein Einsteigerbeispiel für ein Spiel
vorstellen, das einer ECS-Architektur folgt.

## Was ist ECS?

In den oben genannten Artikeln wird näher darauf eingegangen. Zusammenfassend lässt sich ECS jedoch wie folgt beschreiben:

- Entitäten sind eindeutige Identifikatoren.
- Komponenten sind atomare Dateneinheiten, die mit den Entitäten verknüpft sind.
- Systeme sind Funktionen, die auf bestimmte Komponenten angewendet werden.

Die ECS-Architektur löst das Problem der Verarbeitung von Spieldaten, indem sie
die traditionelle Vererbung in der objektorientierten Programmierung (OOP) durch Komposition ersetzt.
Ist ECS eine bessere Lösung? Die Antwort liegt irgendwo zwischen „irgendwie“ und „kommt darauf an“.

## Sollen wir zu ECS wechseln?

Moderne Spiel-Engines nutzen bereits Architektur-Elemente, die dem ECS ähneln, in
ihrem Design. [In seinem Godot-Artikel geht Juan Linietsky](https://godotengine.org/article/why-isnt-godot-ecs-based-game-engine/) auf die Gründe
ein, warum bei der objektorientierten Programmierung (OOP) Bäume und `Nodes` anstelle von ECS verwendet werden. Daraus habe ich folgende
Schlussfolgerungen gezogen:

1. Die Vererbung in Godot mithilfe von `Nodes` ist nicht so ressourcenintensiv, da die Standard-„Komponenten“ ohnehin meist zu den meisten Entitäten hinzugefügt werden.
2. Godot nutzt effiziente „Server“, die die Verarbeitung bestimmter
Datentypen optimieren, um beispielsweise 3D-Modelle zu rendern (`RenderingServer`) oder Physikberechnungen durchzuführen
(`PhysicsServer3D`).

Unity verfolgt einen ähnlichen Ansatz, bei dem die Engine die Komponenten `Renderer`
zusammenfasst und an die Render-Pipeline weiterleitet.

Daher ist der Einsatz von ECS nicht zwingend erforderlich, und es können auch andere effiziente Methoden
genutzt werden. Dennoch möchte ich meine Erfahrungen mit ECS teilen, da ich hoffe, dass sie
jemandem helfen werden, ein besseres Verständnis für das Thema zu erlangen.

## Beispiel

Wenn ich in meinen Privatprojekten ECS-Komponenten entwerfe, versuche ich immer, mir vorzustellen,
anstelle des Spiels eine normalisierte Datenbank zu erstellen. Da SQL laut
[Dfetter, Breinbaas](https://wiki.postgresql.org/index.php?title=Cyclic_Tag_System&oldid=15106) Turing-vollständig ist, erleichtert die Gestaltung der datenbezogenen Spielelemente als
relationale Datenbankstrukturen den Übergang zu einem ECS-Design.

Entwickeln wir ein einfaches Pong-Spiel.

![Umgesetzte Simulation](/images/blog/ecs/pong-sim.js)

Zunächst entwerfen wir eine relationale Datenbank für das Spiel. Die Relationen stellen
ECS-Komponenten dar. Jeder Relationseintrag entspricht einer Instanz einer ECS-Komponente. Die eindeutigen
Schlüssel sind ECS-Entitäten. Gespeicherte Prozeduren, die auf Daten angewendet werden, sind ECS-Systeme.

![Diagramm der Datenbankbeziehungen.](/images/blog/ecs/pong-data.svg "invert")

Die Komponenten `IsRacket` und `IsBall` sind „leer“ und stellen Flags/Tags dar.
Die Komponenten `Position` und `Velocity` enthalten die jeweiligen Positions- und Geschwindigkeitsattribute.
Das Attribut `id` innerhalb der Relation `Entity` ist ein Primärschlüssel und
entspricht den im ECS-Modell vorhandenen Entitäten. Die Attribute `id` in
anderen Relationen sind Fremdschlüssel. Nun der entsprechende PostgreSQL-Code:

```sql
CREATE TABLE Entity(id INTEGER PRIMARY KEY);
CREATE TABLE IsRacket(id INTEGER, CONSTRAINT u_isracket_id UNIQUE(id), CONSTRAINT fk_isracket_id FOREIGN KEY(id) REFERENCES Entity(id));
CREATE TABLE IsBall(id INTEGER, CONSTRAINT u_isball_id UNIQUE(id), CONSTRAINT fk_isball_id FOREIGN KEY(id) REFERENCES Entity(id));
CREATE TABLE Position(id INTEGER, x REAL, y REAL, CONSTRAINT u_position_id UNIQUE(id), CONSTRAINT fk_position_id FOREIGN KEY(id) REFERENCES Entity(id));
CREATE TABLE Velocity(id INTEGER, vx REAL, vy REAL, CONSTRAINT u_velocity_id UNIQUE(id), CONSTRAINT fk_velocity_id FOREIGN KEY(id) REFERENCES Entity(id));
```

Nun sollten wir die gespeicherten Prozeduren erstellen, die die Logik des
Spiels umsetzen. Zunächst eine Funktion, die den Ball bewegt. Nehmen wir an, das Spielfeld ist
512 × 256 groß, der Ball ist 10 × 10 groß, der Schläger ist 10 × 50 groß und befindet sich 5 Einheiten von der
Wand entfernt. Auf der rechten Seite befindet sich eine 5 Einheiten breite Wand. Diese Funktion lässt den
Ball lediglich von allen vier Wänden abprallen.

```sql
CREATE OR REPLACE FUNCTION UpdatePosition(deltaTime REAL)
RETURNS VOID
AS $$
BEGIN
    UPDATE Position SET x=x+Velocity.vx*deltaTime, y=y+Velocity.vy*deltaTime
    FROM Velocity
    WHERE Position.id=Velocity.id;

    UPDATE Velocity SET vx=-ABS(vx)
    FROM Position
    WHERE Position.x>=502 AND Velocity.id=Position.id;

    UPDATE Velocity SET vx=ABS(vx)
    FROM Position
    WHERE Position.x<=20 AND Velocity.id=Position.id;

    UPDATE Velocity SET vy=-ABS(vy)
    FROM Position
    WHERE Position.y>=251 AND Velocity.id=Position.id;

    UPDATE Velocity SET vy=ABS(vy)
    FROM Position
    WHERE Position.y<=5 AND Velocity.id=Position.id;
END;
$$
LANGUAGE plpgsql;
```

Als Nächstes erstellen wir eine Funktion, die den Schläger so anpasst, dass er den
Ball immer perfekt trifft. Wir zielen auf den Ball mit der höchsten Position, also dem maximalen y-Wert, vorausgesetzt,
es ist mindestens ein Ball vorhanden.

```sql
CREATE OR REPLACE FUNCTION UpdateRacket()
RETURNS VOID
AS $$
UPDATE Position SET y=MIN(MAX(t.y - 25, 0.0), 206)
FROM (
	SELECT pos.id as id, (SELECT MIN(p.y) FROM Position p INNER JOIN IsBall b ON p.id=b.id) as y
	FROM Position pos INNER JOIN IsRacket r ON pos.id=r.id
) as t
WHERE Position.id=t.id
$$
LANGUAGE sql;
```

Zum Schluss musst du nur noch die Startwerte festlegen und die beiden Aktualisierungsfunktionen
mehrmals pro Sekunde aufrufen. Leider können „for“-Schleifen nur innerhalb von gespeicherten
Prozeduren existieren, daher packen wir die Schleife in einen `DO`-Block:

```sql
DO
$do$
BEGIN
    INSERT INTO Entity VALUES (0),(1);
    INSERT INTO IsRacket VALUES (0);
    INSERT INTO IsBall VALUES (1);
    INSERT INTO Position VALUES (0,5,0),(1,25,25);
    INSERT INTO Velocity VALUES (1,400,260);

	FOR counter IN 1..60 LOOP
		PERFORM UpdatePosition(1.0 / 30.0);
		PERFORM UpdateRacket();
	END LOOP;
END
$do$;
```

Das in JavaScript umgesetzte Ergebnis siehst du oben auf der Seite. Den
entsprechenden JavaScript-Code findest du im Quellcode-Repository der Website auf
GitHub oder im Quellcode dieser Blogseite (drück `F12`).

Dies ist zwar nur ein sehr einfaches Beispiel, doch derselbe Ansatz würde auch bei
komplexeren Anwendungen funktionieren. Um es klar zu sagen: Ich rate dringend davon ab, Systeme in
anderen Sprachen rund um deren SQL-Implementierung zu entwerfen. Dieser Artikel ist lediglich eine grundlegende
Einführung in ECSxSQL, doch dieser Ansatz hilft mir, mich viel
schneller mit ECS vertraut zu machen.
