# Винаходимо колесо заново разом з ECS

Нещодавно я прочитав [статтю Кейсі Спікмана](https://dev.to/kspeakman/entity-component-system-an-old-new-thing-3224) про проєктування системи «Entity Component System» (ECS).
У ній детально розглядалися подібності та відмінності між архітектурою ECS
та структурованим програмуванням. Були й інші [чудові статті](https://www.simplilearn.com/entity-component-system-introductory-guide-article) на цю
тему, в яких описувалися основні підходи до використання ECS та наводилися різні приклади застосування.

Оскільки я працюю на кафедрі науки про дані та інженерії в ТУМ, я, як правило,
розглядаю системи з більш орієнтованої на дані точки зору, тому я вирішив написати невелику
статтю про використання ECS з моєї точки зору та навести приклад гри для початківців,
яка побудована за архітектурою ECS.

## Що таке ECS?

У наведених вище статтях це питання розглядається більш детально. Однак систему ECS можна коротко описати так:

- Сутності — це унікальні ідентифікатори.
- Компоненти — це елементарні одиниці даних, пов’язані з сутностями.
- Системи — це функції, що оперують конкретними компонентами.

Архітектура ECS вирішує проблему обробки ігрових даних, замінюючи
традиційне успадкування в об’єктно-орієнтованому програмуванні (ООП) на композицію.
Чи є ECS кращим рішенням? Відповідь лежить десь посередині між «так, в деякій мірі» та «залежить від обставин».

## Чи варто нам перейти на ECS?

Сучасні ігрові рушії вже використовують у своїй архітектурі елементи, подібні до ECS.
[У своїй статті про Godot Хуан Лінієцький](https://godotengine.org/article/why-isnt-godot-ecs-based-game-engine/) розглядає аргументи
на користь використання дерев та `Nodes` в рамках ООП замість ECS. З цього я зробив такі
висновки:

1. Спадкування в Godot із використанням `Nodes` не є настільки ресурсоємним, оскільки «компоненти» за замовчуванням
зазвичай і так додаються до більшості об’єктів.
2. Godot використовує ефективні «сервери», які оптимізують обробку даних певних
типів, наприклад, для візуалізації 3D-моделей (`RenderingServer`) або розрахунку фізики
(`PhysicsServer3D`).

Unity використовує подібний підхід, за якого рушій об’єднує компоненти типу `Renderer`
та надсилає їх до конвеєра рендерингу.

Отже, використання ECS не є обов’язковим, і можна
застосовувати інші ефективні методи. Проте я хотів би поділитися своїм досвідом використання ECS, оскільки сподіваюся, що це
допоможе комусь краще зрозуміти цю тему.

## Приклад

Коли я розробляю компоненти ECS у своїх особистих проєктах, я завжди намагаюся уявити собі створення
нормалізованої бази даних замість самої гри. Оскільки SQL є повним за Тюрінгом, згідно
з [Dfetter, Breinbaas](https://wiki.postgresql.org/index.php?title=Cyclic_Tag_System&oldid=15106), проєктування ігрових елементів, пов’язаних із даними, у вигляді
структур реляційної бази даних спрощує перехід до архітектури ECS.

Давайте створимо просту гру «Pong».

![Реалізована симуляція](/images/blog/ecs/pong-sim.js)

Спочатку давайте спроєктуємо реляційну базу даних для гри. Реляції представляють
компоненти ECS. Кожен запис реляції відповідає екземпляру компонента ECS. Унікальні
ключі — це сутності ECS. Збережені процедури, що оперують даними, — це системи ECS.

![Схема зв’язків у базі даних.](/images/blog/ecs/pong-data.svg "invert")

Компоненти `IsRacket` та `IsBall` є «порожніми» і позначають прапорці/теги.
Компоненти `Position` та `Velocity` містять відповідно атрибути положення та швидкості.
Атрибут `id` у відношенні `Entity` є первинним ключем і
відповідає сутностям, присутнім у моделі ECS. Атрибути `id` в
інших відношеннях є зовнішніми ключами. А ось відповідний код PostgreSQL:

```sql
CREATE TABLE Entity(id INTEGER PRIMARY KEY);
CREATE TABLE IsRacket(id INTEGER, CONSTRAINT u_isracket_id UNIQUE(id), CONSTRAINT fk_isracket_id FOREIGN KEY(id) REFERENCES Entity(id));
CREATE TABLE IsBall(id INTEGER, CONSTRAINT u_isball_id UNIQUE(id), CONSTRAINT fk_isball_id FOREIGN KEY(id) REFERENCES Entity(id));
CREATE TABLE Position(id INTEGER, x REAL, y REAL, CONSTRAINT u_position_id UNIQUE(id), CONSTRAINT fk_position_id FOREIGN KEY(id) REFERENCES Entity(id));
CREATE TABLE Velocity(id INTEGER, vx REAL, vy REAL, CONSTRAINT u_velocity_id UNIQUE(id), CONSTRAINT fk_velocity_id FOREIGN KEY(id) REFERENCES Entity(id));
```

Тепер нам слід створити збережені процедури, що реалізують логіку
гри. Спочатку — функцію, яка переміщує м’яч. Припустимо, що ігрове поле має
розміри 512×256, м'яч — 10×10, ракетка — 10×50, а відстань від
стіни становить 5 одиниць. З правого боку розташована стіна шириною 5 одиниць. Ця функція просто відбиває
м'яч від усіх 4 стін.

```sql
CREATE OR REPLACE FUNCTION UpdatePosition(deltaTime REAL)
RETURNS VOID
AS $$
BEGIN
    UPDATE Position SET x=x+Velocity.vx*deltaTime, y=y+Velocity.vy*deltaTime
    FROM Velocity
    WHERE Position.id=Velocity.id;

    UPDATE Velocity SET vx=-ABS(vx)
    FROM Position
    WHERE Position.x>=502 AND Velocity.id=Position.id;

    UPDATE Velocity SET vx=ABS(vx)
    FROM Position
    WHERE Position.x<=20 AND Velocity.id=Position.id;

    UPDATE Velocity SET vy=-ABS(vy)
    FROM Position
    WHERE Position.y>=251 AND Velocity.id=Position.id;

    UPDATE Velocity SET vy=ABS(vy)
    FROM Position
    WHERE Position.y<=5 AND Velocity.id=Position.id;
END;
$$
LANGUAGE plpgsql;
```

Далі створімо функцію, яка оновлює ракетку так, щоб вона завжди ідеально влучала в
м’яч. Ми націлюємося на м’яч із найвищим положенням, тобто з максимальним значенням y, припускаючи, що
існує принаймні один м’яч.

```sql
CREATE OR REPLACE FUNCTION UpdateRacket()
RETURNS VOID
AS $$
UPDATE Position SET y=MIN(MAX(t.y - 25, 0.0), 206)
FROM (
	SELECT pos.id as id, (SELECT MIN(p.y) FROM Position p INNER JOIN IsBall b ON p.id=b.id) as y
	FROM Position pos INNER JOIN IsRacket r ON pos.id=r.id
) as t
WHERE Position.id=t.id
$$
LANGUAGE sql;
```

Нарешті, вам залишається лише задати початкові значення та викликати дві функції оновлення
кілька разів на секунду. На жаль, цикли for можуть існувати лише всередині збережених
процедур, тому ми обгортаємо цикл у блок `DO`:

```sql
DO
$do$
BEGIN
    INSERT INTO Entity VALUES (0),(1);
    INSERT INTO IsRacket VALUES (0);
    INSERT INTO IsBall VALUES (1);
    INSERT INTO Position VALUES (0,5,0),(1,25,25);
    INSERT INTO Velocity VALUES (1,400,260);

	FOR counter IN 1..60 LOOP
		PERFORM UpdatePosition(1.0 / 30.0);
		PERFORM UpdateRacket();
	END LOOP;
END
$do$;
```

Результат, перетворений у JavaScript, можна побачити у верхній частині сторінки.
Відповідний код JavaScript можна знайти у репозиторії вихідного коду веб-сайту на
GitHub або у коді цієї сторінки блогу (натисніть на `F12`).

Це дуже простий приклад, але такий самий підхід спрацює і з більш
складними додатками. Щоб було зрозуміло: я категорично не рекомендую розробляти системи на
інших мовах, орієнтуючись на їхню реалізацію SQL. Ця стаття — лише базовий
вступ до ECSxSQL, але такий підхід допомагає мені набагато
швидше освоїти ECS.
